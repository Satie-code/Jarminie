# 0.4.2 — Conversational Response Generation

**Not a semver git tag** — matching `0.4.1-runtime-stability-and-internet-refactor.md`'s own precedent for a significant, real change that isn't itself a Level-closing milestone. Applied on top of `v0.4.0`'s own still-untagged work (Level 4 itself remains gated on the outstanding manual real-machine verification named in `sprint_4_20.md`'s own completion report).

Date: 2026-08-02
Driven by a direct, explicit user engineering brief (not a numbered Sprint Book sprint): a full end-to-end audit of the conversation pipeline (wake word → STT → Conversation Manager → Memory → Prompt Builder → LLM Client → Decision Engine → Action Engine → TTS), with instructions to replace any placeholder response behavior with real LLM-driven conversation.

## Summary

The audit traced every stage of the live turn-processing path (`voice/pipeline.py`'s `CommunicationPipeline`) against the real, current source — not `docs/STATUS.md`'s own prose — and found one real, live defect matching the user's own description exactly: despite the Decision Engine's Intent Detection and Context Analysis stages (`decision/intent_detector.py`, `decision/context_analyzer.py`) making genuine Ollama LLM calls to *classify* a transcript, nothing in the pipeline ever called an LLM to *generate* the words spoken back to the user for a plain question or casual remark. `Persona.compose_reply()` (`personas/jarvis.py`, `personas/minie.py`) was a fixed string template — `'Understood. You said: "{transcript}".'` — decorated with a memory-content clause and an authority-level prefix, but it never answered anything. This was the literal reply spoken for `EngineSelection.CONVERSATIONAL_RESPONSE`/`INFORM_ONLY`, which is what any question not shaped like a device-control/workflow/scheduler/internet-search request resolves to — the majority of real conversation. It was a deliberate, documented Sprint 3.12 decision at the time ("`compose_reply()` IS the pipeline's Response Generation stage at Level 3," `personas/base.py`'s own docstring), but it contradicted the spec's own architecture (`02_System_Architecture.md`'s Decision Engine pipeline names **Response Generation** as its own stage, after Execution) and left JARMINEI unable to actually answer questions. That decision is reversed here, at the user's explicit request, confirmed via two follow-up clarifying questions in the same session (build real response generation; document it via this changelog-only entry, matching `0.4.1`'s own precedent rather than a full numbered Sprint Book sprint).

Everything else the audit traced was already real and correctly wired: wake word, STT, TTS, the Conversation Manager, Memory, the four specialized engines with real handlers (device control application launch, workflow execution, scheduler reminders, internet research + summarization), and the Decision Engine's classification/retrieval/routing stages. None of those needed changes.

## What Shipped

- **A real Response Generation stage.** New `decision/response_generator.py`'s `ResponseGenerator` reuses `decision/llm_client.py`'s existing `LanguageModelClient`/`OllamaClient` — the exact precedent `internet/summarizer.py`'s `Summarizer` already established for "one subsystem genuinely reusing another's real capability" (Sprint 4.17) — rather than adding a second LLM integration. `generate(transcript, context, decision_trace, persona_name)` builds a prompt from: a small persona-tone lookup (Jarvis professional/direct, Minie warm/caring — the same "small literal lookup, not NLU" discipline as `decision/authority.py`'s `_WORKFLOW_KEYWORDS`), recent conversation turns, retrieved memories (when present) for grounding, and authority-level guidance (INFORM/RECOMMEND/EMERGENCY_ASSIST framing, replacing the old string-prefix approach now that the model writes the whole reply). The prompt explicitly instructs the model to answer directly when it can, ask exactly one brief clarifying question when the request is ambiguous or under-specified, never invent facts it doesn't know, and stay concise (1-3 sentences) since the reply is read aloud by TTS — this is what satisfies "answer, execute, or ask for clarification." `generate()` raises `LlmError` on failure rather than degrading to a safe default of its own: unlike `IntentDetector`/`ContextAnalyzer`/`Summarizer`, this class has no fallback text that belongs to it — the real fallback is `Persona.compose_reply()`'s own template, which lives in `personas/`, a module `decision/` must not depend on (preserving the one-directional dependency `Summarizer`'s own docstring already documents).
- **Wiring.** `main.py` constructs one `ResponseGenerator` per `_construct_level3_modules()` call, reusing the same `OllamaClient` already built there for `IntentDetector`/`ContextAnalyzer` (no second client — unlike `Summarizer`, a conversational reply has no per-engine model-override need). `voice/pipeline.py`'s `CommunicationPipeline` gained a new `_compose_conversational_reply()` method, now the `else` branch of `_handle_turn_complete()`'s engine dispatch (previously a direct call to `PersonaManager.compose_reply_safely()`). It degrades to the old templated reply in exactly two named, honest cases: an empty/whitespace transcript (skips the LLM call entirely rather than asking a model to respond to nothing — Whisper's own no-speech threshold can force `text=""`, `backlog/technical_debt.md` item 9), and an actual `LlmError` from `ResponseGenerator.generate()` (Ollama unreachable, a timeout, an unpulled model) — the same "a narrower catch degrades this one turn rather than the coarse outer catch ending the whole session" reasoning already established for `_handle_scheduler_turn()`'s Sprint 4.19 hardening. A missing `DecisionTrace` (the Decision Engine pipeline itself failed this turn) is deliberately *not* one of the two fallback cases — `ResponseGenerator` tolerates `decision_trace=None`, generating a real reply without trace-derived grounding rather than falling back to the template, since a missing trace is a lesser degradation than a failed LLM call.
- **No changes to `Persona`/`JarvisPersona`/`MiniePersona`/`PersonaManager`.** `compose_reply()`/`compose_reply_safely()` keep their exact signature and template text — they are now the honest, still-tested degraded-fallback path, exactly mirroring how `_handle_scheduler_turn()`/`_handle_internet_agent_turn()` already degrade to canned honest text on failure. Level 2's frozen persona contract and its existing unit tests are untouched.

## Verification

- Every existing test across `tests/integration/`/`tests/system/` that previously pinned the literal `'Understood. You said: "..."'` placeholder (or the transcript itself echoed verbatim, the same template's own tell) as a turn's *final* spoken reply was found via a full-suite run and re-verified against the new real behavior — `tests/integration/test_decision_engine_integration.py`, `tests/integration/test_decision_engine_hardening.py`, `tests/integration/test_communication_pipeline.py`, `tests/integration/test_action_engine_integration.py`, `tests/system/test_level3_acceptance.py`, `tests/system/test_level2_acceptance.py`. Most now assert a real generated reply and inspect the actual prompt sent to the (fake) model for correct grounding (memory content present/absent, authority framing); the one scenario where the template is still the *correct* expected output (Ollama entirely unreachable — `ResponseGenerator`'s own call also fails) is preserved in both its integration- and system-level forms, and each now additionally asserts the new fallback's own log message fired.
- **Real, non-mocked verification**, mirroring this project's own established opt-in real-model precedent (`tests/system/test_level3_real_model_verification.py`): a real local Ollama instance (`llama3:latest`) was reachable in this session, so a real `ResponseGenerator` backed by a real `OllamaClient` was exercised directly (not via the test suite) for three cases — a plain answerable question ("What is the capital of France?" → *"Paris is the capital of France."*), a deliberately ambiguous request ("open that thing again" → the model asked a real clarifying question instead of guessing), and a `RECOMMEND`-authority request (→ the model phrased its answer as a suggestion, per the prompt's own guidance). All three behaved as designed against the real model, not just the fakes.

## Notable Findings During This Work

- `decision/authority.py`'s own header comment claimed `INFORM_ONLY - wired: plain factual answer, no persona flavor`, but before this change `INFORM_ONLY` routed to the exact same templated `compose_reply_safely()` call as `CONVERSATIONAL_RESPONSE` — no distinct "plain factual" handling ever existed. Now moot: both selections share the same real `ResponseGenerator` call, and the prompt's own `AuthorityLevel.INFORM` guidance ("answer plainly, as a simple statement of fact") is what actually delivers that distinction.
- A real, related gap was found and *not* fixed, per the user's own "stop implementing new features" instruction for this session: `CommunicationPipeline._handle_device_control_turn()` always builds a `LAUNCH_APPLICATION` request for any `ACTION_REQUEST` naming a concrete entity, regardless of verb — e.g. "close notepad" would incorrectly try to *launch* notepad.exe. Logged as `backlog/technical_debt.md` item 36.

## Known Deferred Work

The real smoke check above is encouraging but not exhaustive; treat as a known, named, not-yet-closed risk, the same honest framing `Summarizer`'s own adversarial test already established for this class of concern.
