## Summary

JARMINEI reaches `v1.0` — "Official JARMINEI Release" — as a complete personal AI operating system spanning all six locked-spec Levels: Foundation, Communication, Intelligence, Productivity, Companion, and now Autonomous Intelligence & Cognitive Architecture with a full Stabilization pass. Part A (released internally as [0.4.5](0.4.5-level6-part-a.md)) gave JARMINEI the ability to plan, reason about, and evaluate its own actions — a real Planning Engine, Reasoning Engine, Decision Engine v2, Knowledge Graph, a Proactive Assistant that can speak up unprompted, and an Explainability Layer that can answer "why did you suggest that?" with a real, sourced justification, all wired into one continuous autonomous cognitive loop. Part B (this release) closes the loop on production-readiness: real startup/caching optimization, a full async background-task audit, genuine stress and recovery testing against induced failures, a resource-protection mechanism that gracefully degrades non-critical background work under real CPU/RAM pressure, an OS-level secret store (Windows Credential Manager) replacing every plaintext API key and auth token this codebase ever held, a privacy audit giving two previously-unbounded stores real retention limits and a user-facing internet opt-out, a full documentation accuracy pass, and — for the first time in this project's history — real, runnable Long-duration and Resource tests plus a single, consolidated User Acceptance Test checklist naming every manual-verification gap this project has ever disclosed, in one place.

## Notable Bugs Found and Fixed During This Milestone

- **A monkeypatch applied to `UsageTracker._on_tick`/`ReminderEngine._poll_due_items` after the test harness had already constructed and registered them with `TaskScheduler` silently had no effect** — APScheduler holds a reference to the bound method captured at registration time, so a later class-level patch changes nothing the scheduled job actually calls. An early version of Sprint 6.23's own new acceptance test passed for the wrong reason (the assertion happened to be vacuously true) before this was caught and fixed by patching the class *before* the harness fixture runs — the identical technique `test_level6_part_b_resource_protection.py`'s own `job_tick_counts` fixture had already documented for exactly this reason.
- **`stress_app_harness` (Sprint 6.18) constructs its own `TaskScheduler` with `resource_monitor=None`, by deliberate Sprint 6.19 design** — a `resource_sensitive=True` job registered through it can never actually be resource-gated, since `TaskScheduler.add_job()` decides whether to wrap a job at all once, at registration time. Found while writing Sprint 6.23's own acceptance scenario (a real `4 == 0` assertion mismatch, not a vacuous pass); fixed by using `fast_resource_protection_app_harness` (Sprint 6.19's own dedicated, already-verified resource-aware fixture) for that step instead.

- **`backlog/technical_debt.md` item 59** — no "what do you know about me" / data-export / data-deletion conversational or UI surface exists yet, even though every underlying store is fully real and queryable.
