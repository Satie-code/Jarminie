# 0.4.3 — Decision Engine Latency Fix (Real Stop Sequences)

**Not a semver git tag** — matching `0.4.1-runtime-stability-and-internet-refactor.md`/`0.4.2-conversational-response-generation.md`'s own precedent for a significant, real change that isn't itself a Level-closing milestone. Applied on top of `v0.4.0`'s own still-untagged work.

Date: 2026-08-02
Driven by a direct, explicit user engineering brief (not a numbered Sprint Book sprint): a follow-up to `0.4.2` asking whether JARMINEI's own response latency could be reduced, since "time boundary matters" for the product.

## Summary

Real, measured timing against a live local Ollama instance (`llama3:latest`, warm) showed a full conversational turn's 3 sequential LLM calls (Intent Detection → Context Analysis → Response Generation) took **26-30 seconds** — before any STT/TTS/memory-retrieval time. Context Analysis alone accounted for the largest, most disproportionate share (11.9-15.6s), despite producing the shortest *requested* output (5 structured lines). Capturing the raw Ollama response (bypassing `_parse_response()`'s own regex extraction) showed why: the model correctly emits the 5 requested lines, then — because `decision/context_analyzer.py`'s prompt asks for "exactly five lines and nothing else" but never gives Ollama a real stop condition — keeps generating an entire unsolicited extra paragraph of unrelated advice afterward. That paragraph is fully generated, fully timed, and then discarded by the parser; it was pure waste, roughly two-thirds of that stage's own real latency. `decision/intent_detector.py`'s prompt has the identical, if less consequential, gap.

A prompt-only fix (strengthening the "nothing else" wording) was considered first, per the user's own explicit request to try the cheapest option before a bigger change — but a stronger instruction alone does not give Ollama an actual stop condition, and the underlying gap (no `stop` sequence) needed a real interface change to fix reliably. The user confirmed proceeding with that fix.

## What Shipped

- `decision/llm_client.py`'s `LanguageModelClient` Protocol widened additively: `generate(self, prompt: str, timeout_seconds: float, stop: list[str] | None = None) -> str`. Defaulted to `None` (identical behavior to before) so every pre-existing caller/fake needed no change unless it opts in.
- `OllamaClient.generate()` forwards `stop` to Ollama's own real, server-side stop-sequence mechanism (`options={"stop": [...]}`, confirmed against the real `ollama` package's `Client.generate()`/`Options` signatures before writing any code, not guessed) — a real generation control, not prompt-text advice the model can choose to ignore.
- `decision/intent_detector.py` and `decision/context_analyzer.py` now pass `stop=["\n\n"]` — the real, empirically observed boundary between each prompt's own requested structured lines and the model's own unsolicited rambling (neither prompt's legitimate output ever contains a blank line; the model itself reliably inserts one right before it starts wandering off-format).
- `decision/response_generator.py` and `internet/summarizer.py` deliberately pass **no** stop sequence (unchanged) — both are meant to produce free-form natural-language answers where a blank-line stop condition risks truncating a legitimate multi-sentence or multi-paragraph reply. A new regression test (`test_generate_does_not_pass_a_stop_sequence`) proves this is deliberate, not an oversight.

## Verification

- 1117/1119 tests passing (2 correctly-skipped opt-in markers; the 2 observed failures in a full-suite run — both `wait_for_dormant` timeouts in `tests/system/test_level2_acceptance.py`/`test_level4_part_a_acceptance.py` — were confirmed to be this project's own well-documented host-resource-contention flake class, not a regression: both passed cleanly when re-run standalone immediately after), `ruff check .` clean.
- New/updated tests: `decision/llm_client.py`'s own suite gained two tests confirming `stop` is genuinely forwarded to Ollama's `options` (and correctly omitted when not given); `IntentDetector`/`ContextAnalyzer`'s own suites each gained a test confirming the real `["\n\n"]` sequence is passed; `ResponseGenerator`'s own suite gained a test confirming it deliberately passes none.
- **Real, non-mocked verification, not just fakes**: the exact 3-call turn measured before the fix was re-measured after it, twice, against the same real local Ollama instance:

  | Call | Before | After (run 1) | After (run 2) |
  |---|---|---|---|
  | Intent Detection | 4.3-12.6s | 4.37s | 4.37s |
  | Context Analysis | 11.9-15.6s | 5.49s | 3.21s |
  | Response Generation | 6.1-6.5s | 6.06s | 8.40s |
  | **Total** | **26.4-30.6s** | **15.92s** | **15.97s** |

  Context Analysis alone dropped 3-4x; total per-turn LLM latency (still excluding STT/TTS/memory retrieval) dropped by roughly 45%, consistently across repeated runs.

## Known Deferred Work

- STT (Whisper) and TTS (Coqui) latency were not investigated in this pass — the user's own priority was JARMINEI's spoken-reply latency broadly, but this brief specifically chased the confirmed, measured LLM waste first. Worth a separate look if per-turn latency still matters after this fix.
- Response Generation's own ~6-8s is real, intended work (a full natural-language answer), not waste — no further reduction attempted here without a design tradeoff (a smaller/faster model, or streaming synthesis so TTS can start on the first sentence while the rest generates) that wasn't asked for in this brief.
- `stop=["\n\n"]` is a real, working heuristic, not a structural guarantee — a future prompt rewrite for either classifier should re-verify this boundary still holds (e.g., if `ENTITIES:` or another field's own legitimate value could ever contain a blank line, which none currently do).
