## Summary

JARMINEI is now a complete productivity assistant: it can safely act on the desktop it runs on (Part A, released internally as `0.3.1`), and it can now also keep track of time and reach beyond the local machine (Part B, this release). A real Scheduler Engine persists reminders/deadlines and proactively announces one aloud, unprompted, when it becomes due and the system is genuinely idle — this project's first behavior JARMINEI initiates on its own rather than in response to a spoken request. A real Internet Agent turns a live research question into a grounded, cited answer via a real search provider (Brave, provider-agnostic by design) and a real local Ollama summarization pass, honestly labeling which sources corroborate each other rather than presenting an unverifiable "trust me." Both subsystems reuse the exact same `TaskScheduler`/`APScheduler` primitive that also finally gives the memory-cleanup, conversation-purge, and audit-log-purge passes their first genuine recurring cadence — closing gaps tracked since Level 2/3. `v0.4` — "Complete productivity assistant" — is reached with both halves of Level 4 now formally frozen.

## Notable Bugs Found and Fixed During This Level

- **`TaskScheduler.add_job()` fired a job's first execution almost immediately on registration**, not after waiting one full interval — APScheduler's own `IntervalTrigger` defaults its `start_date` to "now." Every real app startup was firing a burst of all five `CommunicationPipeline`-registered jobs (including hourly maintenance passes) within about a second of `CoreManager.startup()` completing. Fixed by explicitly setting `next_run_time`. Found via a genuinely reproducible system-test timing failure, root-caused with a standalone probe script before concluding it was real. See [sprint_4_18.md](../sprint_book/sprint_4_18.md).
- **`database/sqlite_client.py`'s `SqliteClient` had no synchronization around its one `sqlite3.Connection`** — `check_same_thread=False` only disables Python's own same-thread check, not genuine thread-safety. Latent since Sprint 2.7, only exposed once Sprint 4.18 gave `MemoryLifecycleManager`'s two passes their first real, independently-ticking recurring callers on the same connection. Confirmed as a genuine, reproducible defect (not theoretical) via a standalone multi-thread reproduction that reliably corrupted reads; fixed with a `threading.Lock` around every connection-touching method. This same lock was independently verified this release to also structurally close a second, previously-hypothetical race (a background job touching a connection at the exact moment another thread closes it) — confirmed via a direct reproduction before relying on it for Sprint 4.20's own fast-interval system harness. See [sprint_4_18.md](../sprint_book/sprint_4_18.md)/[sprint_4_20.md](../sprint_book/sprint_4_20.md).
- **`BraveSearchProvider.search()`'s own response parsing ran outside its try/except** — a real (if malformed/degraded) `{"web": null}`-shaped API response would have leaked a raw `AttributeError` instead of the promised `SearchError`. Already masked in practice by `ResearchEngine.research()`'s own broad outer catch, but a genuine violation of this method's own documented contract. Found during Sprint 4.20's adversarial re-read; fixed by moving the parsing inside the same try block. See [sprint_4_20.md](../sprint_book/sprint_4_20.md).
