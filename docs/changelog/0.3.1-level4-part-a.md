## Summary

JARMINEI can now safely act on the desktop it runs on, not just talk about it. A real, layered Action Engine (`ActionRegistry`) dispatches every application launch, file/folder operation, window operation, and system command through a permission gate that classifies risk (LOW/MEDIUM/HIGH), enforces allowlists, and requests spoken confirmation for anything beyond LOW risk — with every dispatch persisted to a queryable audit log and, for reversible actions (file/folder delete, application launch), a real, verified-working recovery path. A Workflow Engine lets multi-step action sequences be stored and executed as a unit, with a distinct whole-workflow confirmation for large or high-risk sequences, layered independently on top of each step's own per-action confirmation. This entire surface is wired into live conversation: a voice request to open an application or run a named workflow flows through the same Decision Engine, permission stack, and audit trail as everything else — no bypass, no privileged path.

## What Shipped

- **Device Control** (4.1–4.8) — `device_control/action_engine.py`'s `ActionRegistry`/`ActionExecutor` contract; `ApplicationManager` (launch/close/focus/list, never touching a process it didn't itself launch); `FileOperationsManager` (create/move/copy/rename/delete, hard path-scoping to `allowed_file_roots`, delete always via the OS recycle bin); `WindowManager` (focus/move/resize/minimize/maximize/close any visible window by a real, stable HWND); `CommandExecutionEngine` (a default-deny approved-command allowlist, `shell=False`/argv-only by hard invariant); `ActionResourceGate` (blocks a resource-sensitive action at real CRITICAL CPU/RAM pressure); `security/policy_engine.py`'s `PermissionPolicyEngine` (real per-`ActionType` risk classification) and `security/confirmation_service.py`'s `VoiceConfirmationService` (spoken yes/no confirmation via the active persona's own voice, defaulting to denial on any timeout); `ActionAuditLog` (a persistent, queryable, redacted record of every dispatch) and `ActionRecoveryManager` (real recycle-bin-metadata-parsing restore for deletes, real process termination for launches).
- **Workflow Engine** (4.9–4.10) — `workflow/workflow_model.py`/`workflow_store.py` (`WorkflowDefinition`/`WorkflowStep`, persisted CRUD); `WorkflowExecutor` (runs a stored workflow's steps purely through `ActionRegistry.dispatch()` — no privileged bypass — implementing Part 2's "large workflow rule": a whole-workflow confirmation triggered by step count or any HIGH-risk step, independent of and in addition to each step's own per-action confirmation; `continue_on_failure` per step controls whether a failure aborts the remaining run).
- **Workflow & Device Control Integration** (4.11) — `main.py` constructs and registers the full Level 4 Part A graph alongside Levels 1–3; `decision/authority.py` gained real `DEVICE_CONTROL`/`WORKFLOW` engine routing; `voice/pipeline.py`'s `CommunicationPipeline` gained `_handle_device_control_turn()`/`_handle_workflow_turn()`, giving every previously-isolated Level 4 Part A module its first live caller.
- **Error Handling & Recovery Hardening** (4.12) — the Fail Gracefully Rule applied across six named failure scenarios: application-launch readiness confirmation, file-move copy-then-verify-then-delete safety, command-timeout process termination (already correct, newly verified), `WorkflowExecutor`'s internal fault isolation, `VoiceConfirmationService`'s wrapped speak-then-listen sequence, and `ActionAuditLog`/`ActionRegistry`'s full-body defense-in-depth guarding.
- **Integration Testing & Level Freeze** (4.13) — a full Level 4 Part A Acceptance Pass (`tests/system/test_level4_part_a_acceptance.py`), entirely `tmp_path`-scoped: a live voice-triggered application launch; file create/move/rename/delete with real recycle-bin recovery; window focus/move/minimize against a real, disposable in-process test window; an approved test-only command execution; two multi-step workflows exercising both `continue_on_failure` branches alongside the dual whole-workflow/per-step confirmation layering. Three of Sprint 4.12's six hardening scenarios re-confirmed at the system level; an adversarial re-read of every `device_control/`/`workflow/`/`security/` source file, finding and closing one real, previously-flagged gap (`WorkflowStore.get()`/`list_all()` SQLite hardening).
